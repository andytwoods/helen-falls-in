## 1. Steering model

The mechanic is plausible, but the current specification has three significant risks:

- **Near-centre presses may feel arbitrary.** The player cannot perceive the exact “true centre” at pixel precision. Two apparently identical presses could select opposite directions.
- **Rapid tapping may dominate.** If every press resets correction to a weak initial value, repeatedly tapping can produce safe, low-amplitude steering and bypass the intended commitment.
- **Difficulty may feel noisy rather than demanding.** Wobble, bumps, grooves, rocks, narrowing, grass, and increasing speed all disturb the same lateral state. Without careful telegraphing, deaths will be attributed to randomness.

The important design rule should be: tapping controls the bike by managing persistent momentum. Releasing and re-pressing must not reset the physical steering state.

### Suggested mathematical model

Normalize lateral position to the current path half-width:

- `x = 0`: path centre
- `x = -1` and `x = +1`: hard failure edges
- grass begins around `abs(x) = 0.82`

State variables:

```ts
x       // lateral position
vx      // lateral velocity
steer   // persistent steering/lean state, -1..1
dir     // correction direction sampled on button press, -1 or +1
hold    // duration of current hold
noise   // fast filtered wobble
drift   // slow filtered drift
speed   // forward speed
```

Use a fixed timestep of `dt = 1 / 120`. Rendering can interpolate between simulation states.

On a new press, sample a slightly predictive position:

```ts
const sample = x + predictionTime * vx;

if (Math.abs(sample) > centreDeadzone) {
    dir = -Math.sign(sample);
} else if (Math.abs(vx) > velocityDeadzone) {
    dir = -Math.sign(vx);
} else {
    dir = previousDir;
}
```

This is preferable to literal `-sign(x)`. Inside a tiny centre band, countering current motion matches player intention better than choosing a direction from an imperceptible position error.

While held:

```ts
hold += dt;

const magnitude = Math.min(
    maxCorrection,
    initialCorrection + correctionRamp * hold
);

const targetSteer = dir * magnitude;
steer += (targetSteer - steer) * (1 - Math.exp(-dt / steerResponse));
```

While released:

```ts
hold = 0;
steer += (0 - steer) * (1 - Math.exp(-dt / steerReturn));
```

Crucially, a new press changes `dir` and `targetSteer`, but does not zero `steer`. Reversing an established lean therefore takes time. This prevents high-frequency tapping from producing free, instantaneous damping.

Update filtered wobble using Ornstein–Uhlenbeck noise:

```ts
noise += (-noise / noiseTau) * dt
       + noiseSigma * Math.sqrt(dt) * gaussian();

drift += (-drift / driftTau) * dt
       + driftSigma * Math.sqrt(dt) * gaussian();
```

Then lateral physics:

```ts
const edge = Math.abs(x);
const onGrass = edge > grassStart;

const controlScale = onGrass ? grassControlScale : 1;
const wobbleScale = onGrass ? grassWobbleScale : 1;

const acceleration =
    steeringAcceleration * steer * controlScale
    + wobbleStrength * noise * wobbleScale
    + driftStrength * drift
    + hazardForce;

vx += acceleration * dt;
vx *= Math.exp(-lateralDrag * dt);
x += vx * dt;
```

Starting values worth trying, assuming hard edges at `±1`:

```ts
initialCorrection      = 0.10
correctionRamp         = 2.2 per second
maxCorrection          = 1.0
steerResponse          = 0.09 seconds
steerReturn            = 0.18 seconds
steeringAcceleration   = 3.0 lateral units/s²
lateralDrag            = 0.75 per second

predictionTime         = 0.06 seconds
centreDeadzone         = 0.025
velocityDeadzone       = 0.03

noiseTau               = 0.30 seconds
noiseSigma             = 1.3
wobbleStrength         = 0.30
driftTau               = 2.5 seconds
driftSigma             = 0.22
driftStrength          = 0.30

grassStart             = 0.82
grassControlScale      = 0.55
grassWobbleScale       = 1.5
```

These are only dimensional starting points. Instrument the prototype so every run records `x`, `vx`, `steer`, hold durations, press positions, and cause of death.

### Likely failure modes and remedies

**Rapid tapping becomes optimal**

Do not add an arbitrary input cooldown. Instead:

- Preserve `steer` across releases and presses.
- Make reversal subject to `steerResponse`.
- Make release decay slower than a typical tap interval.
- Measure whether successful players are tapping faster than roughly 8–10 Hz; if so, the input model is probably being exploited rather than mastered.

**Centre sampling feels unfair**

Use the predictive dead-zone rule above. Also make the sprite communicate `vx` and `steer` separately if possible: lateral sliding and bike lean are not the same state.

**Doing nothing is sometimes optimal**

Ensure slow drift will eventually kill an idle player, but avoid strong high-frequency noise. The player should see danger developing and have time to respond.

**Long holds are universally wrong**

A mechanic needs contextual variation. Long holds should occasionally be necessary to recover from grass or a large displacement, even though they are dangerous near centre.

**Random hazards invalidate skill**

Rocks should be visible early enough to anticipate. Grooves need clear visual alignment and consistent physical behaviour. Procedural sequences should have bounded force and recovery time; do not permit a rock, narrowing, and opposite groove to combine arbitrarily.

## 2. Difficulty targets

Five seconds for a first attempt and one to two minutes for an expert is achievable, but probably not through steering parameters alone. A static stochastic system tends either to become solved or to produce increasingly luck-dependent deaths.

The most important knobs are:

1. **Time to edge from a normal error.** This determines reaction allowance.
2. **Lean reversal time.** This determines the skill ceiling and whether tapping works.
3. **Correction ramp.** This determines how punitive a slightly long hold is.
4. **Noise correlation time, not just amplitude.** Slow noise is readable; fast noise feels arbitrary.
5. **Path width.** Small width changes have a very large effect.
6. **Forward speed’s effect on steering and hazard warning time.**
7. **Recovery window between forced disturbances.**

Use speed and path features to extend the curve, but introduce them in controlled phases. For example:

- `0–10s`: broad path, wobble only
- `10–25s`: mild grooves and occasional grass recovery
- `25–45s`: modest narrowing and bumps
- `45s+`: faster combinations, still with enforced recovery gaps

Do not increase wobble, steering sensitivity, speed, and narrowing simultaneously. Players will not understand what changed.

Test the survival targets with distributions, not anecdotes: median first-run survival near five seconds, not average. A few unusually long first runs can distort an average badly.

## 3. Build plan

The broad order is correct, but the greybox milestone is missing several essentials.

Before art, add:

- Input event logging and run replay using recorded inputs and random seeds.
- A deterministic seeded random generator.
- Automated headless simulations for idle play, constant tapping, periodic tapping, and simple feedback controllers.
- Frame-rate tests at 30, 60, 90, and 120 Hz.
- Basic mobile touch testing on real devices.
- Temporary but clear feedback for position, velocity, lean, sampled direction, grass state, and hazard forces.
- A minimal failure/restart loop so restart friction can be evaluated with the mechanic.

Do not wait until after art to test mobile. Capacitor packaging can wait, but the browser prototype should be tested early on actual phones in portrait orientation. Touch feel, viewport behaviour, thermal throttling, and audio restrictions can expose structural problems.

Sliders are useful, but unrestricted live tuning can become impressionistic. Support named parameter presets and export the complete configuration alongside run telemetry.

## 4. Technology

Pixi plus a small fixed-step loop is a good fit. Phaser would provide scenes, input, asset loading, cameras, and audio integration, but this game is simple enough that its extra abstractions may not help. The main risk is not the bespoke loop’s size; it is underestimating all the surrounding lifecycle work:

- pause and resume
- lost focus
- resizing and safe areas
- asset loading
- input deduplication
- audio state
- deterministic randomness
- interpolation
- device performance

For mobile web and Capacitor:

- Listen to `pointerdown`, not `click`.
- Use pointer capture and handle `pointerup`, `pointercancel`, visibility changes, and app suspension. A missed release could otherwise become a fatal permanent hold.
- Set `touch-action: none` and prevent scrolling/zoom gestures on the game surface.
- Avoid separate touch and mouse handlers that can fire twice.
- Unlock or initialise audio during the first user gesture.
- Expect audio suspension after backgrounding and interruptions.
- Account for safe-area insets and changing browser viewport heights.
- Avoid dependence on exact display refresh rate; simulate at a fixed rate and interpolate.
- Timestamp input events and apply them at the correct simulation step where practical.
- Test 60 Hz and 120 Hz phones. The game must not become easier because one device samples input more frequently.
- Add a short startup calibration or accessibility option for touch-hold recognition only if device testing shows it is needed; do not alter core difficulty by platform.

## 5. Highest-value additions

First, make the centre and physics readable without drawing a literal centre line. Path texture, wheel shadow, sprite lean, and subtle lateral camera/parallax cues should help players understand whether they are displaced, moving sideways, or actively steering. If those three states blur together, the game will feel random.

Second, treat procedural generation as authored grammar rather than independent random hazards. Generate short patterns with explicit approach, challenge, and recovery phases. Record the seed and allow instant replay during development. That will make unfair combinations reproducible and turn tuning from guesswork into diagnosis.

One final design issue: choose either time or distance as the canonical score. If forward speed increases, time and distance are no longer interchangeable. Distance better rewards reaching faster late-game sections; time is more immediately understandable. Displaying both is fine, but personal-best rules must use one consistently.
